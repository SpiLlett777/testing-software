# План выполнения лабораторных работ по тестированию ПО

Дата анализа: 18.09.2026. Обновление: веб-стенд, тесты и документы реализованы; фактические результаты и незавершенные
пункты находятся в `docs/STATUS.md`. Мобильная часть отложена. По просьбе пользователя дальнейшие прогоны выполняет
пользователь.

## 1. Вывод и границы проекта

Все задания можно выполнить без базы данных. Предлагается один репозиторий с собственным веб-приложением «Учебный стенд
тестирования», небольшим собственным Android-приложением, тестами и материалами девяти отчетов.

Общий пункт о самостоятельной разработке приложений распространяется на ЛР 1–4 и 6–8. Поэтому для ЛР 7 разрабатываем
свои заметки, несмотря на пример стандартного приложения в тексте задания. ЛР 5 использует публичное API; ЛР 9 — тесты
предыдущих работ.

Не требуется девять отдельных приложений: одни и те же модули можно использовать в нескольких работах. В предоставленном
задании запрета на это нет. Если преподаватель выдаст дополнительные требования, план нужно уточнить.

Текущее состояние каталога: имеются `.idea` и `.venv`; исходников приложения нет. По конфигурации `.venv` используется
Python 3.13.7. Установка остальных инструментов пока не проверена.

## 2. Архитектура без БД

Предлагаемый стек веб-стенда: Python + Flask, HTML/CSS и обычный JavaScript. Он позволяет использовать Python и для
бизнес-логики, и для автотестов, не добавляя отдельную сборку фронтенда. Flask предоставляет средства тестирования
приложения: https://flask.palletsprojects.com/en/stable/testing/.

| Модуль           | Поведение                                                            | Хранение                                               | Лабораторные |
|------------------|----------------------------------------------------------------------|--------------------------------------------------------|--------------|
| Калькулятор      | Сложение, вычитание, умножение, деление, очистка                     | Не нужно                                               | 1, 6         |
| Список задач     | Добавление, завершение, удаление, фильтры                            | localStorage браузера                                  | 2            |
| Логин            | Вход с демонстрационной учетной записью, защищенная страница, Logout | Учебная учетная запись в конфигурации, сессия в cookie | 3            |
| Контактная форма | Имя, email, сообщение, проверка обязательности и формата             | Без сохранения и фактической отправки писем            | 4            |
| Локальный API    | GET `/api/health` с небольшим JSON-ответом                           | Не нужно                                               | 8            |
| Android-заметки  | Добавление и удаление заметки, сохранение, поворот экрана            | Приватный JSON-файл приложения                         | 7            |

Бизнес-логика калькулятора находится в отдельном Python-модуле. Веб-интерфейс вызывает именно ее через сервер, чтобы
unit-тесты проверяли используемый приложением код. Для ЛР 6 добавить метод `is_prime_number` и тестировать его отдельно.

Ограничения хранения: задачи привязаны к браузеру и origin; очистка localStorage удаляет их. Демонстрационная
авторизация не подразумевает регистрацию, восстановление пароля и реальные персональные данные. Контактная форма только
подтверждает успешную валидацию.

Для Todo предусмотреть явно различимые исправный и дефектный режимы, отдельные ключи хранения и сброс данных. Намеренные
дефекты включать только в режиме ЛР 2; остальные модули работают штатно. Список внедренных дефектов хранить отдельно от
пользовательских требований. Возможные дефекты: принятие строки из пробелов, неправильный счетчик незавершенных задач,
удаление неверной задачи после фильтрации. Конкретные дефекты и воспроизводимость фиксируются при реализации.

Android-приложение предлагается сделать на Kotlin с простым нативным интерфейсом и стабильными resource-id. Это
отдельный небольшой модуль репозитория. Адаптивная веб-страница сама по себе не заменяет проверку мобильного приложения
через Appium. Для автоматизации — Appium и UiAutomator2; требования к Android SDK/JDK и совместимые версии уточнить
перед установкой: https://github.com/appium/appium-uiautomator2-driver.

### Уточнения по отдельным работам

- ЛР 1: заранее закрепить поведение при пустом вводе, нечисловом значении, отрицательных/дробных числах, делении на ноль
  и очистке. Сделать 10 тест-кейсов, охватывающих все операции и негативные случаи.
- ЛР 2: адаптировать структуру чек-листа ЛР 1 под задачи, а не переносить проверки арифметики. Баг-репорты первоначально
  можно вести в Markdown, затем перенести в разрешенный заданием Excel-шаблон. Severity описывает влияние, priority —
  очередность исправления.
- ЛР 3: закрывать браузер через fixture/finally даже при падении проверки; использовать явные ожидания. Демонстрационные
  credentials документировать. webdriver-manager включить согласно заданию.
- ЛР 4: для имени, email и сообщения задать по условию валидности и составить полную таблицу из 8 комбинаций; отдельными
  примерами покрыть пустой и некорректный email. Проверять предсказуемые сообщения самого приложения, включая серверную
  валидацию.
- ЛР 5: основной кандидат — JSONPlaceholder, запросы к `/users/1` и `/users`. Проверять статус, обязательные поля/типы и
  переданные значения. API имитирует запись: нельзя требовать, чтобы созданный POST объект появился в следующем GET.
  См. https://jsonplaceholder.typicode.com/guide/. Перед реализацией проверить фактический контракт выбранных запросов.
- ЛР 6: определить поведение `is_prime_number` для отрицательных чисел, 0, 1 и нецелых значений; тесты следуют явному
  контракту. Проверка деления на ноль должна проверять исключение, а UI — его понятное отображение.
- ЛР 7: проверить поворот без потери текста, повторный запуск, фон/возврат, длинные заметки, экранную клавиатуру, жесты
  прокрутки и удаления. Для звонков/SMS и нехватки памяти указать конкретный способ воспроизведения; недоступные
  проверки отметить как не выполненные с причиной. Не подменять системное вытеснение приложения из памяти обычным
  закрытием экрана.
- ЛР 8: нагружать собственный локальный стенд. Использовать сервер без debug/reloader, например Waitress, зафиксировать
  число потоков и ресурсы машины. Цель — сравнить задержки и ошибки при двух уровнях конкурентной нагрузки; эти два
  коротких прогона не доказывают максимальную пропускную способность или длительную устойчивость.
- ЛР 9: основной воспроизводимый workflow запускает unit-тесты и UI-тесты собственного стенда в headless-браузере. Он
  выбирает runner ОС, устанавливает Python и зависимости, запускает сервер, ждет готовности, запускает pytest и
  сохраняет результаты. Тесты публичного API можно вынести в отдельный job. Android и нагрузку не обязательно включать в
  каждый push. Успешный локальный запуск не считается выполнением требования о зеленом GitHub Actions run.

```text

  app/

    unit/
    ui/
      pages/
        base_page.py
        login_page.py
        contact_page.py
    api/
    mobile/
  scripts/
    browser_smoke.py
  mobile/android/
  postman/
  load/k6/
  docs/
    requirements.md
    intentional-bugs.md
    lab01/ ... lab09/
  artifacts/
    lab01/ ... lab09/
  .github/workflows/run-tests.yml
```

В `docs/labNN` хранить подготовку и текст отчета, в `artifacts/labNN` — реальные доказательства выполнения: логи,
результаты и снимки экрана. Файлы приложения и тестов должны быть включены в отчеты как листинги/приложения, а не только
ссылкой на репозиторий. Для каждого отчета фиксировать версию исходников; после исправлений не смешивать старые
результаты с новым кодом.

## 6. Критерии готовности и риски

- Приложения запускаются по README без настройки БД; тестовые данные можно воспроизводимо сбросить.
- Все обычные тесты проходят; намеренные дефекты ЛР 2 изолированы и воспроизводятся по баг-репортам.
- Результаты не выдумываются: подготовленный тест, выполненный тест и успешный тест — разные состояния. Для еще не
  запущенных проверок использовать отметку «не выполнено».
- Для мобильной работы необходимы Android SDK, JDK, Appium, драйвер и устройство/эмулятор. Проверить ресурсы машины и
  аппаратную виртуализацию до настройки эмулятора.
- Для браузерных тестов необходимы браузер и совместимый WebDriver; версии зависимостей закрепить после проверенного
  запуска.
- Внешнее API может быть недоступно или поменять поведение; хранить точные запросы и фактические ответы, не подменять
  публичный API локальным в отчете ЛР 5.
- Для полного завершения ЛР 9 понадобится доступ к GitHub и реальная публикация. Сейчас выполнен только анализ;
  публикация, установка инструментов и запуск тестов не проводились.
- Открытые организационные вопросы: шаблон/титульные листы отчетов и наличие Android-устройства либо рабочего эмулятора.
  Они не мешают начать разработку веб-стенда.

## 7. Ближайший шаг

Реализовать минимальный веб-стенд на Python/Flask без БД и зафиксировать его требования. После этого последовательно
выполнять лабораторные и наполнять отчеты проверенными результатами.
